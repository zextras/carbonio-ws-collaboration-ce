# API & WebSocket Versioning Log

This document tracks internal changes related to API versioning, both for the REST API and the WebSocket.

---

## Version 2.0.0 (unreleased)

Chat moves from MongooseIM/XMPP to REST + WebSocket. `MIGRATION.md` maps every operation; this entry lists
what breaks for a 1.6.x client. It is the change log of 2.0.0 until the first release candidate is tagged.

### Breaking changes (2.0.0)

- **Versioning**: the server accepts only the versions listed in `x-supported-versions` (`["2.0.0"]`). A REST
  request whose `X-WSC-API-VERSION` is any other version (1.6.x included) answers `422` with the server version
  in the header; requests without the header are not checked. A WebSocket handshake that offers only
  unsupported sub-protocols answers `400`.
- **XMPP removed**: no MongooseIM connection (`/services/messaging/ws-xmpp`), no roster. Messages, replies,
  edits, deletes, reactions, forwards, pins, read markers, history, search and export are REST
  (`POST /rooms/{roomId}/messages`, `GET /rooms/{roomId}/timeline`, `PUT /rooms/{roomId}/read`, ...); typing and
  presence are WebSocket. Message ids are generated by the server; clients correlate with `tempId`.
- **Attachments**: `insertAttachmentMultipart` is `POST /rooms/{roomId}/attachments` (was `PUT`), answers `201`
  with the created `Message` and is announced by `MessageReceived`; the `application/octet-stream` upload
  (`insertAttachment`) is removed.
- **Read markers**: `PUT /rooms/{roomId}/read` with `{itemId}` (a message or system event id); markers also
  ride on `GET /rooms/{roomId}/timeline` and `GET /inbox`.
- **WebSocket events**: one socket for everything; chat events are the `WsEvent` family (`MessageReceived`,
  `MessageForwarded`, `MessageEdited`, `MessageDeleted`, `MessagePinned`, `MessageUnpinned`, `ReactionChanged`,
  `ReadUpdated`, `PresenceChanged`, `Typing`). Room and meeting events that create a
  system line carry its author, `systemEventId` and `systemEventCreatedAt`.
- **Presence**: `POST /presence/batch` (at most 100 user ids), `GET /inbox` and `PresenceChanged` carry
  `online` and `lastActivity`.
- **History visibility**: the per-user `clearedAt` floor is enforced by the server on every read path, quotes
  of older messages included; pins are the only exception (`MIGRATION.md` §8).

### Changes against earlier 2.0.0 development builds

- `GET /rooms/{roomId}/messages` is removed: use `GET /rooms/{roomId}/timeline`.
- `MessageReceived.tempId` is echoed to every room member (earlier builds sent it to the sender alone).
- One `MEMBER_ADDED` row and one `RoomMemberAdded` (with its own `systemEventId`) per added member;
  `POST /rooms/{roomId}/members` with an empty list answers `400`.
- Validation: blank `text` answers `400`; `text` at most 8192 characters; `tempId` at most 64;
  `limit` of timeline and search 1 to 200; `{reaction}` at most 32 characters.
- Deleting the pinned message also unpins it (`MessageUnpinned` after `MessageDeleted`); unpinning a message
  that is not pinned is a `204` no-op; pinning or reacting to a deleted message answers `404`; `DELETE` of a
  reaction answers `404` when the message is not in the room.
- `ReactionChanged.operation` (`added`, `removed`) and `Typing.status` (`started`, `stopped`) document their
  values in `asyncapi.yaml`.
- A TEMPORARY-room clear returns and announces the `createdAt` of its `ROOM_HISTORY_CLEARED` row as
  `clearedAt`.
- `api.yaml` documents the `424` that `startMeeting`, `joinMeeting`, `updateMediaStream`, `updateAudioStream`
  and `updateHandStatus` answer while the message broker is down or the video server is not ready (same
  behaviour as 1.6.x; `MIGRATION.md` used to say `403`).
- Send and attachment upload are idempotent on `tempId` for 1 hour per room and sender (`201` with the original message, `409` while the first request is still running); `tempId` is at most 64 characters.

### Versioning rule from the first release candidate

- The 2.0.0 contract (`api.yaml`, `asyncapi.yaml`) is frozen at the first RC tag of CE and ADV.
- After that, an additive change (new endpoint, new optional field or parameter, new event) ships as the next
  `2.0.N`: bump `info.version`, **prepend** the new version to `x-supported-versions` in both specs of both
  editions (lock-step) and add an entry here. Never drop an entry while its shape is still served.
- A breaking change (removed or renamed endpoint, field, event or value; changed status code or meaning) needs
  `3.0.0`, or stays in `2.0.N` only with a `ChangeSet` downgrade registered in `VersionMigrationsRegistry`, so
  that clients on older versions keep receiving the old shape.
- A behaviour fix that changes no shape needs no bump, only a line here.
- Versions that are not in `x-supported-versions` are rejected with `422` (REST) or `400` (WebSocket
  handshake).

## Version 1.6.16

### Changes (1.6.16)

- **API**: Added POST `/meetings/{meetingId}/kick` endpoint (`KickParticipant` body:
  `{ "userToModerate": "<uuid>" }`, required) — kicks the specified participant out of the meeting.
  **Only a moderator (room owner) who is in the meeting can kick**: guests and non-owner members get
  `403 Forbidden`. A moderator cannot kick itself (`400 Bad Request`, use `/leave`), and kicking is
  not allowed in one-to-one meetings (`400 Bad Request`); a missing `userToModerate` returns
  `400 Bad Request`;
  `404 Not Found` when the meeting does not exist, or when the moderator or the user to kick is not a
  meeting participant. Returns `204 No Content` on success. Temporary room members are removed from
  the room when kicked (so in a virtual room they have to go through the waiting room again to rejoin).
- **WebSocket (outbound)**: `MeetingParticipantLeft` now always carries a `reason` field (`LEFT` |
  `KICKED`): `KICKED` when a moderator removed the participant, `LEFT` for every other exit (leave,
  removal from the room, disconnection). Every room member (kicked user included) receives it.

## Version 1.6.15

### Changes (1.6.15)

- **API**: Added `videoSimulcastTiers` capability field to the capabilities response — returns a list
  of `SimulcastTier { name, height }` objects describing the supported simulcast tiers for video.
- **API**: Added PUT `/meetings/{meetingId}/media/quality` endpoint (`MediaQualityRequest` body:
  `userId`, `type`, `mid`, `substream`, optional `temporal`) — lets a subscriber select the
  simulcast spatial/framerate layer for a received video feed.
- **WebSocket (inbound)**: Added `UplinkStatusUpdate` frame — clients send `{ meetingId, changedAt,
  networkScore?, maxUplinkTier?, maxHardwareTier?, to? }` to report their own uplink status.
  `changedAt` is the client wall-clock epoch-ms timestamp; `networkScore` is a 0-10 tier-weighted
  score (omitted when the connection is lost); `maxUplinkTier` / `maxHardwareTier` are publisher
  webcam tiers (`0=LOW`, `1=MEDIUM`, `2=HIGH`, out-of-range values are dropped). Without `to` the
  status is broadcast to all meeting participants; with `to` it is sent only to that participant.
  Frames missing `meetingId` or `changedAt`, or sent by a non-participant, are ignored.
- **WebSocket (outbound)**: Added `MeetingParticipantUplinkStatusChanged` event — relays a
  participant's `UplinkStatusUpdate`; carries `meetingId`, `userId`, `changedAt` and, when present,
  `networkScore`, `maxUplinkTier`, `maxHardwareTier`.

## Version 1.6.14

### Changes (1.6.14)

- **API**: Extended GET `/rooms/{roomId}/attachments` with a new optional `mimeTypeCategory`
  query parameter (enum: `IMAGES` | `VIDEOS` | `DOCUMENTS`). `IMAGES` and `VIDEOS` filter by their
  respective MIME type prefix (`image/`, `video/`); `DOCUMENTS` filters every other MIME type
  (including audio). The parameter is mutually exclusive with the existing free-text `mimeType`
  filter: supplying both in the same request returns `400 Bad Request`.
- **API**: Extended the GET `/rooms/{roomId}/attachments` response with a new `total` field — the
  total number of attachments matching the requested room and filters, excluding cursor pagination.
- **API**: Added GET `/preview/video/{fileId}/{area}/` endpoint — returns a preview (the video's
  first frame, as an image) of the video identified by `fileId`, scaled to `area` (`width x height`, e.g. `320x240`).
  Optional query parameters mirror the image preview endpoint: `quality` (image quality enum), `output_format` (output
  image format enum) and `crop` (boolean, default `false`)
- **API**: Added GET `/preview/video/{fileId}/{area}/thumbnail/` endpoint — returns a thumbnail (the
  video's first frame, as an image) of the video identified by `fileId`, scaled to `area` (`width x height`, e.g.
  `320x240`). Optional query parameters mirror the image thumbnail endpoint: `quality` (image quality enum),
  `output_format` (output image format enum) and `shape` (`Rounded` | `Rectangular`, default `Rectangular`).

## Version 1.6.12

### Changes (1.6.12)

- **API**: Extended GET `/rooms/{roomId}/attachments` with 8 new optional query parameters:
  - `userId` (UUID) — filter attachments by uploader
  - `mimeType` (string) — filter by exact MIME type or prefix (e.g. `image/`)
  - `timestampAfter` (date-time) — filter attachments created strictly after this timestamp
  - `timestampBefore` (date-time) — filter attachments created strictly before this timestamp
  - `minSize` (int64) — filter attachments with size ≥ N bytes
  - `maxSize` (int64) — filter attachments with size ≤ N bytes
  - `orderBy` (enum: `createdAt` | `size`, default `createdAt`) — field to sort by;
      switching to `size` changes the keyset pagination cursor
  - `orderDirection` (enum: `asc` | `desc`, default `desc`) — sort direction
- **API**: Added DELETE `/attachments` endpoint — bulk deletes a list of attachments by their identifiers.
  The request body is `{ "attachmentIds": ["uuid", ...] }` (min 1 item). The requesting user must own
  each attachment or be a room owner of the attachment's room. Guests are forbidden.

## Version 1.6.11

### Changes (1.6.11)

- **WebSocket**: Added `MessageBrokerDisconnected` event — emitted when the backend loses the
  connection to the message broker, so clients can surface a degraded-state indicator.
- **WebSocket**: Added `MessageBrokerRestored` event — emitted when the backend reconnects to
  the message broker, so clients can clear the degraded-state indicator.

## Version 1.6.10

### Changes (1.6.10)

- **API**: Added POST `/meetings/{meetingId}/decline` endpoint — allows the current user to decline
  an incoming meeting invitation. Returns 204 on success, 404 if the meeting is not found.
- **XMPP**: Backend now sends a `meetingStarted` stanza to the room when a one-to-one meeting
  starts, so clients can update the chat history accordingly.
- **XMPP**: Backend now sends a `meetingEnded` stanza to the room when a one-to-one meeting
  ends, so clients can update the chat history accordingly.
- **XMPP**: Backend now sends a `meetingDeclined` stanza to the room when a user declines a
  meeting invitation, so other participants are notified via the chat history.
